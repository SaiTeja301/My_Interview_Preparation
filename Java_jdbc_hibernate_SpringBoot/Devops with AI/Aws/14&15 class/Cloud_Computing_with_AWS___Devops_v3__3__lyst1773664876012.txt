Cloud Service Models

1) IAAS : Infrastructure as a service

2) PAAS : Platform as a service

IAAS : Infrastructure as a service
----------------------------------
--> Provider will provide infrastructure 
    ex: Machines(servers), storage, network
--> We need to take care of platform and application

Your Responsibility: Operating systems, applications, data, runtime, middleware.

PAAS : Platform as a service
----------------------------
--> Provider will provider ready made platform to run our app ( Provider will take care of infrastructure and platform )
ex: AWS Elastic beanstalk

The provider handles the underlying infrastructure and the software environment (operating systems, middleware, databases, web servers). You just focus on your code.

Your Responsibility: Your application code, data, and configuration.


SAAS : Software as a service
-----------------------------
--> Application + Infrastructure + Platform all will be maintained by provider
--> Provider will give their application to run our business

ex: Zoom , Dropbox, Google Drive ........

EBS --> Elastic Block Store
===========================

--> It is a block level storage device ( HDD / SSD )

--> EBS will be attached with EC2 Instance

--> EBS provides both Primary and Secondary storage for EC2 Instances

--> EBS has 2 types of Volumes ( Storage )
  
    -> Root Volume
    -> Additional Volume

=> Root Volume is a default storage which comes whenever we launch a EC2 instance/machine

-> Root Volume is mandatory to have and if we remove root volume from EC2 instance then we cannot start or use the instance/VM

-> Additional Volumes are optional ( we can add or remove any time )

-> For Linux VM, we get around 8 GB as default volume size ( root volume )

-> For windows VM, we get around 30 GB as default volume size ( root volume )

-> EBS Volumes can have upto 16 TB

-> One EC2 VM can have multiple EBS Volumes

-> One EBS Volume can be attached to one EC2 VM at a time not multiple

-> EBS Volumes are specific to Availability Zone
     
                 Mumbai ( ap-south-1)
                 ap-south-1a
                 ap-south-1b
                 ap-south-1c
-> If our EC2 Instance is in ap-south-1a then our EBS volume must also be there in ap-south-1a zone 


EBS Volume Types
==================
1) General Purpose ( Min: 1 GiB, Max: 16384 GiB )

2) Provisioned IOPS ( Min: 4 GiB, Max: 16384 GiB )

3) COLD HDD ( Min: 125 GiB, Max: 16384 GiB )

4) Throughput optimized ( Min: 125 GiB, Max: 16384 GiB )

5) Magnetic ( Min: 1 GiB, Max: 1024 GiB )

IAM Policies --> Permissions 
=============================

What actions are allowed or denied on which aws resources and under what condition

Resource-specific: Permissions are almost always tied to specific AWS resources (e.g., a particular S3 bucket, an EC2 instance, a DynamoDB table).

No inherent identity: A policy on its own does nothing. It's just a set of rules. It needs to be attached to an identity or a resource to take effect.

IAM User
========

A person or application that needs to access AWS.

Has a username and password / access keys.

Can log in to the AWS Management Console or use CLI/API.

Example: “haider” is an IAM user who can start EC2 instances.

IAM Group
===========

A collection of IAM users.

Helps you assign permissions to many users at once.

Example:

Group name: Developers

Attached policy: AmazonEC2FullAccess

→ Every user in that group gets EC2 full access

IAM Role
========

A temporary identity with specific permissions.

No username or password. Instead, AWS services or users assume the role.

Used for giving temporary access or allowing AWS services to talk to each other.

Example:

An EC2 instance assumes a role that allows it to read data from an S3 bucket.

Load Balancer
=============

--> When we deploy our app into a single server then we might/may face the following issues/challenges

    -> One Server trying to handle all requests coming to app 
    -> Increased Burden on the server
    -> Server may slow down leading delayed responses to the clients
    -> Server can crash too
    -> Single Point of Failure

--> To Avoid the above issues, we shall deploy our app into multiple servers and implement the concept of load balancer

--> Load Balancer is used to distribute load to multiple servers in round robin technique

--> The following benefits could be noticed with Load balancer
   
    -> Our App will run on Multiple Servers
    -> Load will be distributed into multiple servers
    -> Burden will eventually reduced on servers
    -> Fast Performance 
    -> High Availability of our app 

-> In AWS there are 4 types of Load Balancers

   -> Application Load Balancer ( http & https )
   -> Network Load Balancer
   -> Gateway Load Balancer
   -> Classic Load Balancer ( Legacy / outdated )

Application Load Balancer (ALB)
===================================
Works at OSI Layer 7
(Application Layer)

Makes routing decision based on url, headers, host, etc
Example : Routes /api/* to one target group and /admin/* to another ..


Network Load Balancer (ALB)
============================

Works at OSI Layer 4 (Transport layer)

Ideal for real-time applications, gaming,......

handles TCP, UDP and TLS traffic with very high performance and low latency


Gateway Load Balancer
======================

 It is an AWS load balancer that distributes traffic to security appliances like firewalls for inspection before forwarding it to application servers.

What GWLB does

1️⃣ Traffic comes from internet
2️⃣ GWLB sends traffic to firewall appliances
3️⃣ Firewall inspects packets
4️⃣ If safe → forwarded to application
5️⃣ If malicious → blocked

Why Auto Scaling?
====================

During events like Big Billion Day Sale, traffic is unpredictable.

You can't manually scale fast enough.

Auto Scaling helps by:
======================

Increasing instances when traffic goes up

Decreasing instances when traffic goes down

✅ Benefits of Auto Scaling:
==================================
Fault Tolerance

If an instance fails, another is launched automatically.

Cost Management

Only run the number of servers needed, saving money during low traffic.

High Availability

Keeps your application running smoothly under heavy load.

Versioning 
===============
--> Versioning is a means of keeping multiple variants of an object in the same bucket. You can use versioning to preserve, retrieve, and restore every version of every object stored in your Amazon S3 bucket. With versioning, you can easily recover from both unintended user actions and application failures.

--> By default versioning is disabled for S3 bucket 
  ( Whenever we add new same file again in bucket it will replace or override the old one and if you don't want to replace old object with new from bucket then we can go with Versioning )
